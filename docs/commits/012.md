## Notas y límites

- `ConfigModule` valida el entorno al importar `AppModule` (D-72): las pruebas de duración del JWT sustituyen `ConfigService` con el entorno ya validado, y el análisis de `CORS_ORIGINS` y de la duración se cubre con pruebas unitarias. El comportamiento real de arranque se comprobó con la API compilada, como se describe arriba.
- Las pruebas de la migración 2FA (J-07) ahora deshacen primero la migración de roles.
- El preflight de un origen no listado responde `204` con métodos y cabeceras, pero sin `Access-Control-Allow-Origin` (comportamiento estándar del middleware); el navegador lo rechaza.
- **Postman:** las dos colecciones de `postman/` se actualizaron: las aserciones de los claims del JWT esperan `mocca-go-api`/`mocca-go-client` (fallaban antes del cambio) y la carpeta nueva «07b» cubre al repartidor (login, `/auth/me`, 200 en catálogo, 403 en escrituras, `/users` y `/movements`) y el `400` al crear un `cliente`. La colección local se ejecutó con newman 6 contra la API compilada y una base limpia con seed: carpetas 00 a 07b y 09, **235 peticiones, 610 aserciones, 0 fallos**. Las carpetas opcionales 08 (bloqueo) y 10 (429) no se ejecutaron. La colección de despliegue recibió el mismo cambio, sin ejecutarse (apunta a una URL que se vuelve a crear). Usa las variables nuevas `courierUsername` y `courierPassword` (`change-courier-password`, el valor de `.env.example`).
- **Acción local:** si ya tenías el volumen `inventory_data`, ejecuta `docker compose down -v` una vez para que PostgreSQL cree `mocca_go` (ver README), y añade `SEED_COURIER_PASSWORD` y las variables nuevas a tu `.env`.
- **Railway:** el proyecto se vuelve a crear; hay que cargar `DB_*`, `JWT_SECRET`, `ACCESS_TOKEN_TTL_SECONDS`, `CORS_ORIGINS`, `TRUST_PROXY_HOPS=1` y las tres contraseñas del seed. Los enlaces de despliegue del README corresponden al despliegue anterior.
